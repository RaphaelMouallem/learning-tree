# Learning Tree

Turn "I want to learn X" into a small, navigable tree the person can actually finish, and keep it alive: track progress, expand it as they advance, export it.

The design rule behind everything: **`tree.json` stores structure; the node `.md` files store content and checkboxes; progress is always computed from the checkboxes, never stored.** Two sources of truth drift apart, so there is only one.

## When to use this skill

Use it whenever the person wants to learn something with a structured path, even if they never say "learning tree". Typical phrasings: "learning path", "roadmap", "curriculum", "study plan", "how do I learn X", "what should I learn next", "plan my learning of X". Also use it to resume, update, expand, check progress on or export an existing tree (a `tree.json`, a learning-tree zip or folder). Offer `minimal` mode to people who want freedom rather than a prescribed path.

Skip it for one-off questions ("what is a closure?"), single explanations, or quizzes with no plan behind them.

## Glossary

Everyday speech says "node" for the big area. Here the words are fixed, so use them the same way with the person:

| Term | Meaning |
|---|---|
| Tree | One learning goal ("Learn Git") |
| Gear | A big capability area ("Foundations", "Collaboration"); 4-8 per tree |
| Skill node | One demonstrable thing inside a gear; 3-6 per gear |
| Capstone | Proof the gear stuck: build a small project or write it up; 1 per gear |
| `nodes` (in `tree.json`) | The generic list holding every gear, skill node and capstone; "node" in JSON means any item |

## The tree in one picture

```
Tree
└── Gear            a capability you could name ("Write and run programs")   4-8 per tree
    ├── Skill node  one demonstrable thing, 1-10 hours                       3-6 per gear
    └── Capstone    prove the gear: build a project OR write it up           1 per gear
```

Only three levels exist, on purpose. Tasks (todos) live inside node files, never in the tree. Exact limits and how to apply them: `references/granularity-rules.md`.

## Modes

Set `config.mode` in `tree.json`. Pick from the person's wording; default to `guided`.

| Mode | When | What you produce |
|---|---|---|
| `minimal` | "just the tree", "no resources", "let me explore" | Gears + skill nodes with hours. No resources, todos or capstones. Progress is tracked with a `done` flag per node. |
| `guided` (default) | most requests | Everything, but expand **only the active gear**; expand the next when the person finishes or asks. |
| `full` | "build it all now" | Everything, all gears expanded up front (warn that links age and that this takes long). |

A minimal tree can be upgraded later: "enrich the Memory gear" adds resources, todos and a capstone for that gear only. Config keys and their effect: `references/tree-schema.md`.

## Where files live

```
<tree-folder>/            e.g. learning/rust/  or  <vault>/Learning/rust/
├── tree.json             structure: gears, skills, capstones, prerequisites, config
├── nodes/<slug>.md       one file per skill/capstone: resources, todos
└── overview.md           GENERATED by scripts/export.py - never edit by hand
```

Ask where to create the folder only if you cannot infer it (an Obsidian vault path, the current project). In a sandbox without persistent storage, see "Resuming and exporting".

## Workflow: new tree

1. **Intake.** Ask at most three things, skipping any already answered: the goal (what they want to *do* with it), current level, hours per week. If they named a mode, use it.
2. **Research the shape of the topic.** Do not invent gears from memory when current practice matters. Search for existing roadmaps and syllabi first (see `references/sources.md`) and base gears on what experienced practitioners and curricula agree on.
3. **Draft gears only** (4-8): title, one-line outcome, estimated hours. Show them and get a go-ahead or edits before generating more. Reorder by dependency and fill `requires`.
4. **Expand** per mode: skill nodes (3-6 per gear) with `est_hours`.
5. **Write node files** (guided/full). Read `references/node-template.md` and `references/vetting-rubric.md` first. Each skill node gets one primary video, one primary article, up to three optional alternatives, and 3-7 todos.
6. **Add a capstone** per expanded gear (guided/full): offer a build option and a write-up option tailored to the gear, with 2-4 acceptance criteria.
7. **Validate, then summarize.** Run `scripts/validate_tree.py`, fix every error, and consider every warning. Then show the person a compact summary: gears with hours, what is expanded, total hours and roughly how many weeks at their pace. Do not paste the JSON. Mention where the files are and offer an export.

Never write a URL you did not get from a search or fetch in this session. A tree with fewer, verified links beats a full one with invented links. If a niche topic has thin resources, say so.

**If you have no web search or fetch tool:** you cannot verify the shape of the topic or any link, so do not pretend to. Tell the person once, in a sentence, why: "I can't search the web here, so I'll build the tree only (gears and skill nodes, drawn from my own knowledge) and leave resources out." Then set `config.mode` to `minimal`, write no URLs and no resource lines, and say the gear structure is unverified against current curricula. Offer to enrich specific gears later, in a session that has search. If they want resources anyway, give search phrases they can run themselves (`references/sources.md`, "Query patterns") rather than names or links from memory.

## Tracking and updating

- The person ticks `- [ ]` boxes (in Obsidian or any editor) or tells you what they finished. **Tick a box only for something they said they did.** Completion is theirs to claim. When they report progress in chat, record it with `scripts/edit_tree.py <folder> tick <node> <items>` rather than editing files by hand; it uses the same counting rules as `progress.py`, so the numbers cannot disagree.
- After any change, run `scripts/progress.py` and report: what moved, what is next. Lead with the next action, not a data dump.
- When a gear is done (or the person asks), expand the next available gear. `progress.py` lists gears ready to expand.
- "Too easy / too hard / skip this": `scripts/edit_tree.py <folder> skip <node>` (skipped nodes never inflate or deflate the percentage), or split/merge nodes per `references/granularity-rules.md`. Do not delete nodes that have ticked boxes.
- To add a node or gear later, use `edit_tree.py <folder> add skill <slug> --title "..." --parent <gear> --hours N --scaffold`, then fill in the scaffolded file (`<fill: ...>` markers; the validator warns until they are gone).
- "Already know this": mark skipped, or tick the todos if they can demonstrate them - ask which they prefer.
- "I want to go deeper on this node": offer to promote it to its own tree (reserved; see `references/tree-schema.md`, "Sub-trees").

## Resuming and exporting

**Resume** when the person uploads a zip or folder, or mentions an existing tree: unpack it, run `scripts/validate_tree.py` and `scripts/progress.py`, summarize where they are, and propose the next node.

**Export** with `scripts/export.py <tree-folder>`: it validates, regenerates `overview.md` (progress, a Mermaid map, per-gear details), refreshes a generated "Position in tree" link block at the bottom of each node file (so Obsidian's graph shows the real structure; pass `--no-node-links` to skip), and writes a zip named `<tree_id>-learningtree-<date>.zip`. Add `--canvas` for an Obsidian canvas of the tree. Hand the zip to the person where your environment allows file delivery.

In environments where files do not persist between conversations (e.g. a hosted chat sandbox), tell the person once, early: *the tree travels as the zip*. End each working session with an export and ask them to upload it next time. Where files do persist (a local agent, an Obsidian vault), skip the zip unless asked.

## Scripts

All scripts are standard-library Python. Run from the skill folder, or pass absolute paths.

| Script | Use |
|---|---|
| `scripts/validate_tree.py <folder> [--strict]` | Structure errors (must fix) and size/quality warnings. Run after every edit. |
| `scripts/progress.py <folder> [--json]` | Node/gear/tree percentages, statuses, next actions, gears ready to expand. |
| `scripts/check_links.py <folder>` or `--url ...` | Detects dead links. `blocked` means unverified, not dead; `error` means retry. Skips localhost/private addresses unless `--allow-private`. |
| `scripts/edit_tree.py <folder> tick\|untick\|skip\|unskip\|add ...` | Record progress and change structure without hand-editing JSON. Validates before writing; on error nothing changes. |
| `scripts/export.py <folder> [-o file.zip] [--no-zip] [--canvas]` | `overview.md`, node link blocks, optional `tree.canvas`, zip bundle. |
| `scripts/canvas_export.py <folder>` | Just the Obsidian canvas (also reachable via `export.py --canvas`). |

Run `check_links.py` after writing resources and before delivering. If the network is restricted it reports `error`; say the links are unverified rather than claiming they work.

**If you cannot run code:** read each node file, count `- [x]` versus `- [ ]` under the `Todos`/`Acceptance criteria` headings (ignore items marked `(optional)` and everything under `Alternatives`), and compute percentages by hand using the rules in `references/tree-schema.md`. It is slower, but nothing else changes.

## Portability notes

- Say "web search" and "fetch a page", not product-specific tool names; use whatever the current agent offers.
- Everything is plain files. Do not rely on any one app's features.
- For Obsidian users, follow `references/obsidian.md`.
